# 동작 원리와 분류 기준

LG Display 특허 트렌드 센싱이 특허를 받아 숫자와 요약으로 만드는 과정, 분류 정확도, 분류 기준을 자세히 적은 문서임.
앱 사용법은 [README](../README.md), 배포·백업은 [OPERATIONS.md](OPERATIONS.md), 설계 이유는 [ARCHITECTURE.md](ARCHITECTURE.md)에 있음.

## 1. 전체 그림 — 숫자로 보는 흐름

실제 DB 기준임 (2026-11-10).

```
   수집 88,197건
      │   자사 46,161 · 삼성디스플레이 39,522 · 중국 4사 2,514
      │
      │  규칙으로 기술 분야 판정 (AI 안 씀)
      ▼
   IPC 코드로 판정       66,730건  (75.7%)
   키워드로 판정          9,053건  (10.3%)
   명칭으로 판정          8,350건  ( 9.5%)
   초록으로 판정          2,212건  ( 2.5%)
   미분류                 1,852건  ( 2.1%)
      │
      │  DB에서 건수·증감률·급증 용어 계산 (AI 안 씀)
      ▼
   1차 4종 × 2차 8종 × 3차 50종 분야별 추이
   신기술 후보: 급증 용어 50개 + 초기 신호 20개
      │
      │  계산된 숫자만 AI에게 주고 문장을 쓰게 함
      ▼
   분기 자동 요약 13개 (전체 1 + 방식 4 + 기술 분야 8)
   기술 분석 보고서 (분야를 골라 누르면 근거 특허를 읽고 작성)
      │
      │  코드가 AI 문장의 숫자·근거를 다시 대조함
      ▼
   화면 5개
```

수집한 특허의 97.9%가 기술 분야를 받음. 무작위 검증으로 잰 정확도는 약 85%임.
**숫자는 전부 DB가 계산하고, AI는 문장만 씀.** 이게 이 시스템의 핵심 원칙임.

## 2. 어디서 무엇을 가져오나

소스는 KIPRIS Plus Open API(특허·실용 공개·등록공보) 한 곳임.

| 회사 | KIPRIS 검색어 | 건수 | 가장 오래된 출원 |
|---|---|---|---|
| LG디스플레이 (자사) | 엘지디스플레이 | 46,161건 | 1987년 |
| 삼성디스플레이 | 삼성디스플레이 | 39,522건 | 2003년 |
| BOE | 보에 테크놀로지 | | |
| CSOT | 차이나 스타 옵토일렉트로닉스 | 중국 4사 합계 2,514건 | 1999년 |
| Tianma | 티안마 | | |
| Visionox | 비젼녹스 | | |

KIPRIS는 무료로 쓰면 한 달에 1,000번까지 부를 수 있음. 처음 전체 수집에 약 200번, 이후 새 특허 받기는 보통 4번 씀.

### 왜 "LG디스플레이"로 검색하지 않나

실제로 해봤음. `LG디스플레이`로 검색하면 **0건**이 나옴.
KIPRIS에 등록된 출원인 이름이 `엘지디스플레이 주식회사`이기 때문임. 그래서 `엘지디스플레이`로 검색함.

### 중국 회사는 이름을 걸러서 받음

KIPRIS 출원인 검색은 이름 일부만 맞아도 결과에 넣어 줌.
`티안마`로 검색하면 전혀 다른 회사인 "닝보 케**티안 마**그넷"까지 나옴.
그래서 받은 뒤 회사 이름이 정확히 맞는 것만 남김. Visionox는 한국 표기가 "비젼녹스"라서 이걸로 찾음.

## 3. 파이프라인 — 단계별 설명

특허 한 건이 화면의 숫자와 요약이 되기까지 거치는 과정임. 순서대로 설명함.

### 0단계 · 대상 회사 목록 읽기

어느 회사를 받을지는 `backend/src/kipris.js`의 `APPLICANTS`, `CHINA_APPLICANTS`에 적혀 있음.
회사를 추가하거나 빼려면 이 목록만 고치면 됨.

### 1단계 · 수집

KIPRIS에서 명칭, 초록, 출원인, 출원일·공개일·등록일, 상태, IPC 코드, 도면 주소를 받음.

- 처음에는 전체를 받고(`npm run collect`), 그 뒤로는 **마지막으로 받은 날짜 이후** 새로 공개·등록된 것만 받음.
- 중간에 끊겨도 다시 실행하면 이어서 받음.
- 개발 중에는 같은 요청을 디스크에 저장해 두고 다시 쓰기 때문에, 시험하느라 무료 한도를 낭비하지 않음.
- 출원번호 같은 긴 숫자가 숫자형으로 바뀌면 끝자리가 깨지기 때문에, 받은 값은 전부 문자로 다룸.

청구항은 여기서 받지 않음. 특허 1건당 KIPRIS를 1번 불러야 해서, 8.8만 건을 다 받으면 한도를 88번 넘김.
화면에서 "청구항 불러오기"를 누른 특허만 받아 저장함 (지금 29건).

### 2단계 · 저장

원본은 `patents` 테이블에 그대로 둠. **분류 결과는 다른 테이블(`classification`)에 따로 씀.**
분류 기준이 바뀌어도 원본은 건드리지 않고 분류만 다시 계산하면 되기 때문임.

### 3단계 · 기술 분야 분류 ★

여기가 숫자의 정확도를 정하는 곳임. 1차 → 2차 → 3차 순서로 정함.

- **1차(방식):** OLED · LCD · 공통 · 마이크로LED
- **2차(기술 분야):** 회로 · 광학 · 공정 · 소자 · TFT 소자 · 설계 · 기구 · 재료
- **3차(세부 기술):** 50종 (6장 참고)

판정 순서는 IPC 코드 → 키워드 → 명칭 → 초록임. 앞에서 정해지면 뒤는 안 봄.

**IPC 코드는 모두 보고 점수를 더함.** 처음에는 첫 번째 IPC 하나만 봤는데, 검토해 보니 5건 중 3건이 틀렸음.
첫 코드가 "액정 전반"처럼 넓은 코드이거나, 발명의 핵심이 아닌 부수 기술인 경우가 많았기 때문임.
그래서 대응표에 있는 IPC를 전부 보고, 2차 분야마다 점수를 더해 가장 높은 쪽을 고름.

**키워드는 띄어쓰기와 대소문자를 무시함.** 특허 문서에 "화소 회로"와 "화소회로"가 섞여 있기 때문임.

**장비 특허는 따로 잡음.** "라미네이션 장치", "검사 장치"처럼 공정 말 + 장치로 끝나는 명칭은 공정으로 봄.
이런 특허에도 패널 IPC가 붙어 있어서, 점수만 보면 광학이나 터치로 잘못 가는 일이 많았음.

**왜 AI로 분류하지 않나.** 같은 특허가 돌릴 때마다 다른 분야로 가면 추이 그래프를 믿을 수 없음.
그래서 무작위 100건을 사람이 채점하고 → 틀린 이유를 찾아 규칙을 고치는 일을 11번 넘게 반복해 정확도를 올렸음.

**3차는 키워드 → IPC 추정 → 기타 순서로 정함.** 명칭·초록에 세부 기술 키워드가 없으면, 2차를 정한 IPC 코드의 3차를 씀.
이렇게 IPC로 정한 3차는 화면에 **'IPC 추정'** 표시가 붙고, 특허 목록의 '3차 근거' 필터로 빼거나 그것만 볼 수 있음 (2026-11 담당자님 피드백).
IPC→3차 규칙은 실제로 맞는지 표본을 채점해 고른 9개만 남겼음 (116개 중). 건수가 많은 규칙 26개를 규칙마다 10~20건씩, 모두 290건을 명칭·초록으로 채점해 75% 이상 맞은 규칙만 남김.
남긴 규칙: 공정 장비(H10P 72)·포장(B65D)·레이저 가공(B23K 26) → 패널 제조·가공, 증착 마스크(C23C 14) → 증착·패터닝, AR·VR(G02B 27/01, H04N 13), 백라이트(G02F 1/13357), 액정 배향(G02F 1/1337), 패드·본딩(G02F 1/1345).
남긴 규칙의 표본 정확도는 건수 가중으로 약 88%임. 규칙별 채점 결과는 `backend/classification/ipc_level3_validation.csv`에 있음.
처음에는 "키워드 결과와의 일치율"(`npm run ipc-check --prefix backend`)로 골랐는데, 실제 채점과 크게 달라서(예: 일치율 77%였던 봉지 규칙이 실제로는 15%) 채점 결과로 바꿨음.

분류 기준은 코드가 아니라 CSV 파일(`backend/classification/`)에 들어 있음. IPC 대응 157줄, 키워드 361줄임.

### 4단계 · 집계

화면의 모든 숫자는 여기서 SQL로 계산함. AI는 쓰지 않음.

날짜 기준이 두 가지라 헷갈리기 쉬움.

| 화면 | 기준 | 이유 |
|---|---|---|
| 연간 출원 추이 그래프 | **출원일** | 기술이 언제 나왔는지 보려고 |
| 대시보드 숫자, 최근 공개 동향 | **공개일** | 최근에 무엇이 새로 보이기 시작했는지 보려고 |

**최근 1~2년 출원은 음영과 점선으로 표시함.** 특허는 출원하고 보통 18개월 뒤에 공개됨.
그래서 2025년 출원은 아직 대부분 안 보이고, 그래프로 그리면 출원이 폭락한 것처럼 보임.
실제로 줄어든 게 아니라 아직 공개가 안 된 것이라서, 실선 대신 점선으로 그리고 "미공개 출원 반영 전"이라고 적음.

**1년 전 건수가 30건 미만이면 증감률을 안 보여 줌.** 2건이 5건이 되면 +150%인데, 이런 숫자는 의미가 없음.

### 5단계 · 신기술 탐지

최근에 갑자기 많이 나온 용어를 찾음. 이것도 AI 없이 계산함.

1. 명칭과 초록에서 1~3어절짜리 명사구를 뽑음
2. 한 특허에 여러 번 나와도 1번으로 셈
3. 전체 특허의 8% 넘게 나오는 흔한 말("표시 장치" 같은)은 뺌
4. 최근 2년과 그 전 4년을 통계(로그우도비)로 비교해 **우연이 아닌 증가**만 남김
5. "OLED"와 "유기 발광"처럼 뜻이 같은 표기는 하나로 묶음

실제 결과 (최근 2년 9,141건 vs 그 전 4년 16,024건):

```
화소정의막      371건 → 481건
회로층          193건 → 312건
증착용 마스크    11건 →  92건
멤브레인          0건 →  64건   ← 초기 신호 (예전엔 없던 말)
반사 전극        28건 →  87건
```

예전에 0건이었다가 최근 3건 이상 나온 용어는 "초기 신호"로 따로 보여 줌. 지금 20개임.

### 6단계 · AI 동향 요약 ★

AI가 분야 하나의 흐름을 정해진 일곱 칸(맨 위 핵심 메시지 한 줄, 핵심 흐름, 성장 분야, 경쟁사 동향, 주목 특허, 시사점, 한계)으로 정리함. 핵심 메시지와 시사점은 2026-11 담당자님 피드백으로 추가함.

**AI에게는 계산이 끝난 숫자만 줌.** 건수, 증감률, 비중, 급증 용어, 근거 특허를 DB에서 먼저 계산해 넘기고,
AI는 그걸 읽고 문장만 씀. AI가 직접 세거나 계산하게 하면 숫자를 지어내기 때문임.

근거 특허는 "가장 많이 늘어난 세부 기술"에서 최근 공개순으로 뽑음. 중요도 순위는 아님.

**프롬프트는 칸마다 나눠 둠.** 한 번에 일곱 칸을 다 쓰게 하면 칸끼리 내용이 겹쳐서, 목적별 네 파일로 나눠 따로 부름.
고칠 때는 코드가 아니라 `backend/prompts/`의 파일을 고치면 됨.

| 파일 | 맡은 칸 |
|---|---|
| `01_stats.md` | 핵심 메시지 |
| `02_timeline.md` | 핵심 흐름 · 성장 분야 |
| `03_competitors.md` | 경쟁사 동향 |
| `04_evidence.md` | 주목 특허 (원문 문장 번호만 고르게 하고, 문장은 원문에서 그대로 가져옴) |

시사점은 검증된 출원 통계로, 한계는 표본 크기와 공개 지연을 보고 코드가 씀.

### 6-2단계 · AI 기술 분석 보고서 ★

동향 요약이 "몇 건 늘었나"를 쓴다면, 기술 분석 보고서는 **"어떤 기술이 무엇을 위해 어디로 가나"** 를 씀.
AI 동향 요약 화면에서 분야와 기간을 고르고 누르면 만들어지고, 한 번 만든 보고서는 저장해 두고 다시 보여 줌.

1. **근거 특허 고르기 (코드):** 시기마다 급증 용어가 나온 특허와 늘어난 분야의 특허를 회사별로 고름 (자사 5 · 삼성 5 · 중국 4사 3건)
2. **청구항 보강 (KIPRIS):** 초록이 200자보다 짧은 특허는 청구항을 받아 함께 넘김 (보고서 1개당 최대 12번 호출)
3. **AI를 목적별로 네 번 부름:** ① 특허 분석(6건씩 나눠 동시에) → ② 시기별 흐름 · ③ 경쟁사 비교(동시에) → ④ 핵심 결론
4. **검사 (코드):** 원문에 없는 목적·효과를 붙였는지, 재료·위치 관계를 뒤집었는지(예: 도핑 대상), 회사 의도를 단정하는 말(전략·선점·시장 등)을 썼는지 봄

숫자(KPI 카드·차트)는 동향 요약처럼 DB가 계산함. 원문에 없는 목적을 일반 지식으로 추정했으면 '(추정)'을 붙이게 하고,
근거 특허 표에는 특허마다 해결 문제와 기존 대비 개선점을 적음 (처음 3건만 보이고 '더보기'로 펼침).
Claude Haiku 5.5로 보고서 하나에 약 40초 걸림 (OLED > 회로, 근거 특허 39건 기준 43초).

**설정만 바꾸면 다른 AI로 교체됨.** AI를 부르는 코드는 `backend/src/ai.js` 한 곳뿐이고,
주소·키·모델 이름 세 가지만 바꾸면 OpenRouter든 사내 AI 서버든 그대로 동작함.
배포 서버는 운영팀이 준 OpenRouter 키로 Claude Haiku 5.5(`anthropic/claude-haiku-5.5`)를 씀. 개발 초기에는 무료 모델로 기능을 시험했음.

### 7단계 · 요약 검사

AI가 쓴 요약을 코드가 다시 읽고 문제를 찾아 화면에 표시함.

| 검사 | 찾는 것 |
|---|---|
| 이상한 숫자 | 넘겨준 자료에 없는 숫자 |
| 수치 대조 | 숫자가 있어도 회사·분야·연도·지표(건수·비중·증감률)가 맞는 짝인지 |
| 특허 섞임 | 특허 A 설명에 특허 B 내용이 들어간 것 |
| 과한 해석 | "주력", "집중하는", "중단"처럼 회사 의도를 단정하는 말 |
| 형식·분량 | 일곱 칸 중 빠진 칸, 칸마다 정한 글자 수 |

문장마다 어느 자료에서 나왔는지 따라가서(출처 추적), 근거가 약한 문장에는 화면에 '주의'를 붙임.
검사 결과는 숨기지 않고 요약 위에 그대로 보여 줌.

개발 초기 무료 모델로 만든 자동 요약은 13개 중 4개만 검사를 깨끗하게 통과했음.
그 뒤 프롬프트를 나누고 검사를 보강했고, 요약마다 검사 결과를 쌓아 두어 아래 명령으로 통과율을 볼 수 있음.

```powershell
npm run summary-quality --prefix backend -- 30
```

최근 30일 요약을 모델·분류 기준별로 묶어 검사 통과율을 보여 줌. AI는 부르지 않음.

### 8단계 · 자동 실행

서버가 켜져 있으면 한 시간마다 확인하고 알아서 돌림.

- **새 특허 받기:** 마지막으로 성공한 갱신에서 90일이 지나면 실행함.
  정해진 날짜가 아니라 "마지막 갱신으로부터 며칠"로 세기 때문에, 서버가 그날 꺼져 있었어도 다시 켜지면 밀린 걸 바로 함.
  실패하면 한 시간마다 다시 부르지 않고 하루 쉼.
- **AI 동향 요약:** 분기가 바뀌면(1·4·7·10월) 13개를 새로 만듦. AI가 바쁘면 잠깐 쉬었다 다시 시도하고,
  중간에 실패한 것은 6시간 뒤 이어서 만듦.

그래서 화면에 새로고침 버튼이 없음.

### 9단계 · 화면

DB에서 숫자를 꺼내 그래프와 표로 그림. 그래프는 라이브러리 없이 SVG로 직접 그림.
음영, 점선, 키보드로 값 보기처럼 이 프로젝트에만 필요한 표시를 자유롭게 넣기 위해서임.


## 4. 분류 정확도와 한계 (자세히)

### 분류 정확도: 1차 약 93% · 2차 84% · 3차 약 66%

기준 v0.5.6으로 무작위 100건을 뽑아 1·2·3차를 함께 채점하고, 규칙을 고친 뒤(v0.5.8) 같은 100건으로 다시 잰 값임 (2026-11-22, 맞음 1점·애매 0.5점).
채점은 명칭·초록을 보고 Claude가 판단했고, 100건이라 ±8%p 정도 오차가 있음. 건별 결과는 `backend/classification/accuracy_check_v0.5.6.csv`.

| 단계 | 정확도 | 주로 틀린 곳 |
|---|---|---|
| 1차 (방식) | 약 93% | 방식별 표본(각 20건)을 엄격하게 채점해 건수로 가중한 값. 처음엔 OLED 전용 구동 회로가 공통으로 가서 공통이 70%였음 → 아래 1차 규칙 수정 후 93% |
| 2차 (기술 분야) | 81% → 84% | 아래 2차 규칙 수정 후 같은 100건에서 3건이 고쳐지고 망가진 건 없음. 남은 오류는 명칭이 "표시 장치"처럼 일반적이고 IPC가 패널 코드뿐인 기구(패드·연성회로) 특허 |
| 3차 (세부 기술) | 62% → 약 66% | 처음엔 '기타'가 23건인데 그중 맞는 세부 기술이 있었던 게 대부분이었음. 아래 2차 수정과 3차 키워드 보강 후 같은 100건에서 다시 잼 |

2차는 v0.5.5 때 100건씩 11번 채점한 평균(약 85%)과 비슷함.

**1차 규칙 수정 (2026-11-22):** OLED 키워드에 '전계발광'·'유기전계', 마이크로LED 키워드에 '마이크로 엘이디'를 추가하고,
방식 코드·키워드가 없을 때 구동 회로 IPC로 1차를 정하게 함 (G09G 3/30·3/32 → OLED, G09G 3/36 → LCD, 둘 다 있으면 공통).
그 결과 공통 6,630건이 OLED 5,175건·LCD 1,435건·마이크로LED 20건으로 옮겨감 (공통 24,035 → 17,406건). 2·3차는 바뀌지 않음.
방식별 채점 기록은 `backend/classification/accuracy_check_level1_v0.5.6.csv`.

**2차 규칙 수정 (2026-11-22):** 2차는 IPC 점수 + 키워드 점수로 정하는데, 명칭이 일반적이면 IPC가 거의 항상 이김.
- 키워드 추가: '윈도우'(기구, 명칭 주제어로도), '스퍼터'·'성형'·'기판 처리'(공정 장비), '가요성 회로'(패드·본딩), '광원 구동'(회로)
- 봉지 코드(H10K 50/84·842·844)는 본문에 봉지·밀봉·투습·침투·실링 같은 말이 없으면 넓은 코드로 봄. 이 코드로 소자가 된 913건 중 506건은 그런 말이 없었고 대부분 커버·보호 필름·지지 부재 같은 기구 특허였음
- 시험 후 되돌린 것: 명칭이 일반적이면 모든 2차를 후보로 열기(백라이트 모듈이 기구로 감), 넓은 코드뿐일 때 IPC 점수 절반(맞던 특허가 재료로 감)
- 결과: 2차 561건 바뀜(소자 → 기구·설계·광학 등). 바뀐 것 중 무작위 50건을 보면 나아진 것 26, 나빠진 것 8, 둘 다 애매 16. 정답 세트 109건은 85% 그대로

**3차 키워드 보강 (v0.5.8, 2026-11-22):** '기타' 특허에 자주 나오는데 다른 세부 기술 특허에는 드문 용어 56개를 추가함.
- 예: 어레이 기판·배선 ← 데이터 라인·신호 라인·링크 배선·팬아웃·정전기 / 터치·센서 ← 입력 감지·감지 전극 / 발광 구조·탠덤 ← 정공 수송·전자 수송 / 백라이트 ← 램프 / 영상 처리 ← 디더링·그레이 스케일
- 새 키워드는 `keyword_map.csv`의 `level3_only` 칸에 1을 달아 **3차를 고를 때만** 씀. 처음엔 2차 점수에도 들어가서 회로·광학 특허 수백 건이 TFT 소자로 끌려갔음
- 결과: '기타' 20,050 → 17,713건(22.7% → 20.1%). 2차는 바뀌지 않음. 새로 3차를 받은 것 30건 중 맞음 21·애매 5·틀림 4, 다른 세부 기술로 바뀐 330건 중 20건을 보면 나아짐 13·나빠짐 2

특히 3차 "기타"가 17,713건(20.1%)으로 많음. 맞지 않는 IPC 추정을 빼면서 v0.5.5의 6,635건(7.5%)에서 23.3%까지 늘었다가, 키워드 보강(v0.5.8)으로 줄였음. 더 보강해야 함.
3차를 IPC로 추정한 특허는 812건(0.9%)이고 'IPC 추정'으로 표시됨. 1·2차 분류는 바뀌지 않았음.

### 최근 1~2년 출원은 아직 다 안 보임

특허는 출원 후 약 18개월 뒤 공개됨. 2025~2026년 출원은 지금 보이는 게 전부가 아님.
그래프의 점선 구간을 "줄었다"로 읽으면 안 됨.

### AI 문장은 검사를 거쳐도 사람이 확인해야 함

개발 중 무료 모델로 만든 자동 요약은 13개 중 9개가 검사에 하나 이상 걸렸음.
자료에 없는 숫자를 쓰거나, 특허 A를 설명하면서 특허 B 내용을 섞거나, "주력한다"처럼 회사 의도를 단정했음.

배포 서버는 Claude Haiku 5.5로 바꿨고, 프롬프트를 칸마다 나누고 검사를 보강했음.
배포 주소에서 시험한 요약 1건은 35초 걸렸고 숫자 불일치는 0건이었음.
기술 분석 보고서는 특허 원문을 해석하므로 '(추정)'·'주의'가 붙은 문장은 근거 특허 표에서 원문을 확인할 것.
여러 모델을 같은 조건으로 비교 평가하는 일은 아직 못 함.
설정 세 줄(`AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL`)만 바꾸면 되도록 만들어 둠.
모델을 바꿔도 검사는 그대로 두고, 중요한 숫자는 근거 표와 근거 특허로 확인하는 게 안전함.

### 중국 4사는 실제보다 작게 보임

한국 특허청에 낸 출원만 집계함. 중국 본토 출원은 안 들어 있음.
Tianma는 최근 5년 한국 출원이 0건이라 그래프에 거의 안 보임.

### 패밀리·후속 출원이 같이 세어짐

같은 기술을 여러 건으로 나눠 낸 것도 각각 1건으로 셈. 특정 연도 증가폭이 실제보다 크게 보일 수 있음.

### 마이크로LED는 아직 표본이 적음

1차 마이크로LED는 86건뿐임. IPC 코드(`H10H`)만으로는 일반 LED(백라이트 등)가 섞여서,
본문에 "마이크로 LED"가 나올 때만 마이크로LED로 봄.

### KIPRIS 한도가 있음

KIPRIS는 월 1,000번 한도라 전체 수집을 자주 할 수 없음. 그래서 새 특허만 받는 방식으로 돌림.

### 공용 서버 하나에서만 돎

DB가 SQLite 파일 하나라 여러 서버에서 같이 쓸 수 없음. 서버가 꺼져 있으면 자동 갱신도 안 돎.

## 7. 분류 기준이나 대상 회사를 바꾸고 싶다면

### 분류 기준

`backend/classification/` 안의 CSV를 고침.

`ipc_map.csv` — IPC 코드로 분야 정하기

```
ipc_prefix,level1,level2,level3
H10K,OLED,,
H01L 51,OLED,,
```

`keyword_map.csv` — 키워드로 분야 정하기

```
level1,level2,level3,keyword,requires
OLED,,,유기발광,
OLED,,,OLED,
```

같은 형식으로 한 줄을 추가하면 됨. `H10K`처럼 앞자리만 적으면 그 그룹 전체, `G02F 1/13`처럼 `/` 뒤까지 적으면 그 숫자로 시작하는 코드만 해당함.
같은 코드에 여러 줄이 맞으면 가장 길게(구체적으로) 적힌 줄을 씀.

고친 뒤 재분류함. KIPRIS는 안 부름.

```powershell
npm run classify --prefix backend
```

고치기 전에 팀에 먼저 알릴 것. 분류가 바뀌면 모든 화면의 숫자가 바뀜.

판정 규칙을 바꿔 결과가 달라지면 `backend/src/classification.js`의 `CRITERIA_VERSION`을 올릴 것. 배포 서버는 켜질 때 새 기준의 결과가 없으면 자동으로 전체를 다시 분류하고, 예전 버전 결과는 지움(약 10~20초).
기준을 올리면 AI 동향 요약도 새 기준으로 다시 만들어야 하고, 자동 요약을 켠 서버는 그 분기 요약을 새로 만듦(AI 비용 발생).

### 대상 회사

`backend/src/kipris.js`의 `APPLICANTS`(자사·삼성)와 `CHINA_APPLICANTS`(중국 4사)를 고침.
회사를 추가했다면 그 회사 특허를 새로 받아야 함 (KIPRIS 호출 필요).

```
patent-trend/
│
├─ backend/                       서버
│   ├─ src/
│   │   ├─ index.js               ★ 서버 시작점. 자동 실행도 여기서 켬
│   │   ├─ kipris.js              KIPRIS 호출, 대상 회사 목록
│   │   ├─ sync.js                새 특허 받기 → 저장 → 분류
│   │   ├─ scheduler.js           90일 자동 갱신, 분기 자동 요약
│   │   ├─ classification.js      ★ 기술 분야 분류기 (판정 순서가 여기 있음)
│   │   ├─ trendData.js           추이·공개 동향 집계
│   │   ├─ emerging.js            신기술 탐지 (급증 용어)
│   │   ├─ ai.js                  AI 호출 (AI는 이 파일에서만 부름)
│   │   ├─ trendSummary.js        ★ AI 동향 요약 (자료 만들기, 프롬프트 조립)
│   │   ├─ summary*.js            요약 검사·수치 대조·출처 추적·시사점·품질 기록
│   │   ├─ techReport.js          ★ AI 기술 분석 보고서 (근거 특허 선정, 4단계 프롬프트, 검사)
│   │   ├─ autoSummary.js         분기 자동 요약
│   │   ├─ patentSummary.js       개별 특허 요약
│   │   ├─ siteAuth.js            접속 비밀번호 (loginPage.js가 입력 화면)
│   │   ├─ db.js                  테이블 정의
│   │   └─ routes/                API 주소별 처리
│   ├─ prompts/                   ★ 동향 요약 프롬프트 4개 (칸별)
│   ├─ classification/            ★ 분류 기준 CSV (분류를 고치려면 여기)
│   ├─ scripts/                   수동 실행 명령 (수집, 재분류, 자동 요약, AI 사용량)
│   ├─ data/patents.db            데이터 저장소
│   └─ .env                       API 키 (각자 PC에만, 공유 안 됨)
│
├─ frontend/                      화면
│   └─ src/
│       ├─ App.jsx                ★ 사이드바, 상단 검색, 화면 전환
│       ├─ index.css              디자인 (색 변수, 라이트/다크)
│       ├─ pages/                 화면 5개
│       └─ components/            그래프, 필터, 표, 특허 상세, 기술 분석 보고서(TechReport.jsx), 아이콘
│
├─ docs/ARCHITECTURE.md           설계와 기술 선택 이유
└─ CLAUDE.md                      Claude로 작업할 때 지킬 규칙
```
