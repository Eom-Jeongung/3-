# 구조와 설계

이 문서는 "LG Display 특허 트렌드 센싱"이 어떻게 만들어졌고 왜 그렇게 정했는지 설명함.
무엇을 하는 시스템인지, 어떻게 돌리는지는 [README](../README.md)를 볼 것.

## 1. 한눈에 보는 구조

프로그램은 두 덩어리임. 화면(frontend)과 서버(backend).

```
   ┌─────────────── 브라우저 ───────────────┐
   │  React 화면  (frontend/)                │
   │  사이드바 · 대시보드 · 그래프 · 표       │
   └──────────────────┬─────────────────────┘
                      │  /api/... 요청 (JSON)
                      ▼
   ┌─────────────── 서버 ───────────────────┐
   │  Express  (backend/src/)                │
   │   ├─ routes/      주소별 처리            │
   │   ├─ 집계·분류·신기술 탐지   (AI 없음)    │
   │   ├─ ai.js        AI 호출 (여기서만)     │
   │   └─ scheduler.js 자동 갱신·자동 요약    │
   └───────┬──────────────┬─────────┬───────┘
           │              │         │
           ▼              ▼         ▼
      SQLite 파일     KIPRIS API   AI API
      patents.db      (특허 원천)   (OpenAI 호환)
```

- 화면은 서버에만 요청함. KIPRIS나 AI를 화면이 직접 부르지 않음. 키가 브라우저에 노출되지 않게 하기 위해서임.
- 서버는 평소에는 DB만 읽음. KIPRIS는 새 특허를 받을 때와 청구항을 불러올 때만, AI는 요약을 만들 때만 부름.

### 개발할 때와 배포할 때

| | 개발 (`npm run dev`) | 배포 (`npm run build` → `npm run start`) |
|---|---|---|
| 화면 | Vite 개발 서버가 따로 띄움. 고치면 바로 반영 | 미리 만든 파일(`frontend/dist`)을 Express가 같이 내보냄 |
| 서버 | 파일을 고치면 자동 재시작 | 한 번 켜 두면 계속 돎 |
| 포트 | 화면 5173 · 서버 4000 (천안 서버는 `$PORT` · `$PORT+100`) | 서버 포트 하나 |

개발 중에는 화면이 `/api` 요청을 서버 포트로 넘겨 줌(`frontend/vite.config.js`의 proxy). 그래서 화면 코드에는 서버 주소가 없음.

## 2. 사용 기술과 고른 이유

| 구분 | 사용한 것 | 버전 |
|---|---|---|
| 언어 | JavaScript | |
| 실행 환경 | Node.js | 22.12 이상 |
| 서버 | Express | 5 |
| DB | SQLite (`better-sqlite3`) | |
| 화면 | React | 19 |
| 화면 개발 도구 | Vite | 8 |
| 코드 검사 | oxlint | |
| 특허 데이터 | KIPRIS Plus Open API | |
| AI | OpenAI 호환 `/chat/completions` (지금은 OpenRouter 무료 모델로 시험 중) | |

라이브러리를 최소로 씀. 서버는 `express`, `better-sqlite3`, `fast-xml-parser`(KIPRIS가 XML로 답함) 세 개뿐이고,
화면은 `react`, `react-dom` 두 개뿐임. 그래프·아이콘·화면 전환도 직접 만들었음.

### 왜 Python이 아니라 JavaScript인가

1. **화면은 어차피 JavaScript임.** 브라우저에서 돌아가는 화면은 JavaScript로만 만들 수 있음.
   서버를 Python으로 만들면 언어가 두 개가 되고, JavaScript로 만들면 하나로 끝남.
2. **배워야 할 언어가 적을수록 유리함.** 팀원 대부분이 둘 다 익숙하지 않았음. 하나만 익히면 화면과 서버를 모두 읽고 고칠 수 있음.
3. **서버와 화면이 같은 형식(JSON)을 그대로 주고받음.** 변환 코드가 필요 없음.
4. **설치가 단순함.** Node.js 하나로 서버·화면·라이브러리 설치가 해결되고, `npm run dev` 하나로 둘 다 켜짐.
5. **이 프로젝트가 하는 일에 충분함.** KIPRIS 호출, 저장, 규칙 분류, 집계, AI 호출 모두 JavaScript로 잘 됨.

Python이 확실히 유리한 일도 있음. 형태소 분석, 임베딩을 직접 계산하는 일, 대량 통계 분석임.
실제로 신기술 탐지는 팀원이 Python(형태소 분석기 kiwipiepy)으로 먼저 만들었고, 이걸 JavaScript로 옮기면서 형태소 분석 대신 조사·어미를 떼는 규칙으로 바꿨음.
결과는 거의 같았지만, 앞으로 이런 일이 커지면 그 부분만 작은 Python 서비스로 떼어 붙이는 방법이 있음.
API 주소만 같게 맞추면 화면은 고칠 필요가 없음.

### 왜 SQLite인가

- 설치할 게 없음. 파일 하나가 곧 DB라 복사해서 주고받으면 끝임.
- 이 규모(8.8만 건, 약 370MB)에서는 충분히 빠름. 대시보드 숫자를 계산하는 데 0.07초임.
- `better-sqlite3`는 결과를 바로 돌려주는 방식이라 코드가 단순함 (기다리는 코드 `await`가 필요 없음).

단점은 여러 사람이 같은 데이터를 함께 쓰기 어렵다는 것임. 8장 참고.

### 왜 차트 라이브러리를 안 썼나

그래프는 SVG로 직접 그렸음(`TrendChart.jsx`, `DashCharts.jsx`).
"미공개 출원 반영 전" 음영, 공개가 덜 된 연도의 점선, 자사·삼성은 같은 눈금이고 중국 4사만 따로 잡는 눈금,
키보드 화살표로 값 보기처럼 이 프로젝트에만 필요한 표시가 많았음. 라이브러리로는 오히려 맞추기 번거로웠음.

## 3. 요청 하나가 처리되는 길

### 대시보드를 열 때

```
브라우저                      서버                              DB
  │  GET /api/trends/overview   │                                │
  ├────────────────────────────▶│  trendData.js                  │
  │                             │  최근 12개월·1년 전·2년 전       │
  │                             │  공개 건수, 분야별 건수,          │
  │                             │  많이 늘어난 세부 기술 계산 ─────▶│
  │                             │◀───────────────────────────────┤
  │◀────────── JSON ────────────┤                                │
  │  GET /api/trends/series     │  연도별·분야별 출원 건수 ────────▶│
  │◀────────── JSON ────────────┤                                │
  │  KPI 카드·그래프·도넛 그림    │                                │
```

AI도 KIPRIS도 부르지 않음. 그래서 빠름.

### AI 동향 요약을 새로 만들 때

```
브라우저                서버                                        AI
  │ POST /api/summaries   │                                          │
  ├──────────────────────▶│ 1. trendSummary.js가 DB에서 숫자 계산     │
  │                       │    (건수, 증감률, 비중, 급증 용어, 근거 특허)│
  │                       │ 2. 숫자를 표로 만들어 프롬프트에 넣음 ─────▶│
  │                       │◀──────────── 다섯 칸 문장 ────────────────┤
  │                       │ 3. summaryCheck.js가 답을 검사             │
  │                       │ 4. 요약 + 넘긴 숫자 + 검사 결과를 함께 저장 │
  │◀──── 요약 + 검사 ──────┤                                          │
```

한 번에 수십 초~1분 넘게 걸림. 그래서 화면은 먼저 저장된 요약(`GET /api/summaries`)을 보여 주고,
새로 만들기는 사용자가 누를 때만 하거나 분기 자동 실행에 맡김.

**넘긴 숫자(facts)도 같이 저장함.** 요약에 이상한 숫자가 있으면 AI가 무엇을 보고 썼는지 나중에 확인할 수 있게 하기 위해서임.

## 4. 화면 구조

```
App.jsx  사이드바 · 상단 검색 · 화면 전환
 ├─ HomePage       대시보드         DashCharts (KPI 작은 선, 연간 추이, 도넛)
 ├─ FieldPage      기술 분야별 분석  FieldPicker, TrendSection → TrendChart
 ├─ SummaryPage    AI 동향 요약     FieldPicker, AiSummaryPanel
 ├─ EmergingPage   신기술 탐지
 ├─ PatentsPage    특허 목록        FilterBar, PatentTable, usePatentList
 └─ PatentDetail   특허 상세        PatentSummary   (어느 화면에서나 열림)
```

### 화면 전환은 주소의 # 뒤로 함

`#/field?level1=OLED&level2=설계`처럼 고른 분야가 주소에 남음.
새로고침해도 그 화면이 그대로 열리고, 주소를 복사해 팀원에게 보내면 같은 화면을 볼 수 있음.
라우터 라이브러리 없이 `App.jsx`에서 주소를 읽어 화면을 고름.

### 대시보드와 특허 목록은 지우지 않고 숨김

다른 메뉴로 갔다 와도 특허 목록의 검색어·필터·펼친 목록이 그대로 남게 하기 위해서임.
나머지 화면은 열 때마다 새로 그림.

### 특허 목록은 나눠서 받음

8.8만 건을 한 번에 받지 않고 10건씩 받음(`usePatentList`). "더보기"를 누르면 다음 10건을 붙임.
필터를 바꾸면 처음부터 다시 받고, 늦게 도착한 이전 응답은 버림.
검색어는 글자를 칠 때마다 요청하지 않고 0.3초 기다렸다 보냄.

### 디자인은 색 변수로만

색은 `index.css` 맨 위 `:root`의 변수로만 씀. 다크 모드는 운영체제 설정을 따라 자동으로 바뀜.

| 변수 | 쓰는 곳 |
|---|---|
| `--accent` | 보라 포인트 (선택된 메뉴, 버튼, 링크) |
| `--own` · `--competitor` · `--china` | 자사 · 삼성 · 중국 4사 (선, 태그, 아이콘) |
| `--series-1` ~ `--series-8` | 분야별 그래프 선 |
| `--surface` · `--bg` · `--hairline` | 카드, 바탕, 테두리 |

**분야 색은 분야를 따라감.** 기간이나 회사를 바꿔도 OLED는 항상 같은 색임. 그래프를 넘겨 볼 때 헷갈리지 않게 하기 위해서임.

## 5. 데이터베이스

파일 하나(`backend/data/patents.db`)에 테이블이 들어 있음. 테이블 정의는 `backend/src/db.js`에 있음.

### 원본

| 테이블 | 내용 |
|---|---|
| `patents` | 특허 원본. 출원번호, 명칭, 초록, 출원인과 구분(own · competitor · china), 출원일 · 공개일 · 등록일, 상태, 도면 주소 |
| `patent_ipc` | 특허별 IPC 코드 (한 특허에 여러 개) |
| `patent_claims` | 대표 청구항 (상세에서 불러온 특허만) |
| `sync_log` | 특허 받기 기록. 언제, 수동인지 자동인지, 몇 건 받았는지, 성공했는지 |

### 분류

| 테이블 | 내용 |
|---|---|
| `classification` | 1·2·3차 분류 결과, 판정 근거(IPC · 키워드 · 명칭 · 초록), 기준 버전 |
| `application_tags` | 응용 태그 |
| `ipc_map` · `keyword_map` · `tag_map` | 분류 기준 (CSV에서 읽어 넣음) |

### AI

| 테이블 | 내용 |
|---|---|
| `trend_summaries` | AI 동향 요약. 범위·기간, 모델, 요약 본문, 넘긴 숫자, 근거 특허, 검사 결과, 걸린 시간, 수동/자동 |
| `summary_runs` | 분기 자동 요약 실행 기록 |
| `patent_summaries` | 개별 특허 요약 (다시 만들어도 이전 것을 남김) |
| `ai_calls` | 모든 AI 호출 기록. 용도, 모델, 입력·출력 토큰, 걸린 시간, 오류 |

### 예전 DB에만 남은 테이블

`tech_category_stats`, `scraps`, `ask_log` 테이블과 `patents.tech_category` 칸은 데모 v1과 지금은 뺀 AI 질문 기능에서 쓰던 것임.
코드에서는 지웠기 때문에 새로 만드는 DB에는 생기지 않음. 이미 있는 DB에는 데이터를 지우지 않으려고 그대로 둠.

### 원본과 분류를 나눈 이유

분류 기준은 계속 바뀜(v0.1 → v0.5.5). 원본에 분류를 같이 적으면 기준을 바꿀 때마다 원본을 고쳐야 함.
나눠 두면 `classification` 테이블만 지우고 다시 계산하면 됨. KIPRIS를 다시 부를 필요가 없음.

## 6. API

| 주소 | 하는 일 | 주요 조건 |
|---|---|---|
| `GET /api/trends/overview` | 최근 12개월 공개 동향, 늘어난 세부 기술, 마지막 갱신 시각 | |
| `GET /api/trends/series` | 출원 추이 | `years` 1~10, `unit` year·half, `company`, `level1~3` |
| `GET /api/trends/emerging` | 급증 용어, 초기 신호 | `months` 12·24·36, `company`, `level1~3` |
| `GET /api/patents` | 특허 목록 | `q` 검색어, `applicant_type`, `status`, `open_from·to`, `level1~3`, `sort`, `order`, `limit`, `offset` |
| `GET /api/patents/filter-options` | 필터 선택지 | |
| `GET /api/patents/:id` | 특허 상세 | |
| `POST /api/patents/:id/claims` | 청구항 불러오기 (KIPRIS 1회) | |
| `GET /api/patents/:id/summary` | 저장된 개별 특허 요약 | |
| `POST /api/patents/:id/summary` | 개별 특허 요약 새로 만들기 (AI) | |
| `GET /api/summaries` | 저장된 AI 동향 요약 | `level1~3`, `from`, `to` (빼면 최근 3개 연도) |
| `POST /api/summaries` | AI 동향 요약 새로 만들기 | 같은 조건을 body로 |
| `POST /api/sync` | 새 특허 받기 | 화면 버튼은 없앴고 자동 갱신이 대신함 |

## 7. 설계하면서 정한 것들

### 숫자는 DB, 문장은 AI

AI에게 특허 목록을 주고 "늘어난 분야를 찾아 줘"라고 하면 숫자를 지어냄.
그래서 계산은 전부 SQL로 하고, AI에게는 계산이 끝난 표만 줌. AI가 하는 일은 그 표를 읽고 문장을 쓰는 것뿐임.
같은 이유로 `temperature`를 0으로 둬서 같은 자료면 최대한 같은 답이 나오게 함.

### AI는 한 파일에서만, 표준 형식으로만

AI 호출은 `ai.js`의 `chat()` 하나뿐임. 특정 회사의 SDK나 전용 기능 없이 OpenAI 호환 `/chat/completions`만 씀.
그래서 `AI_BASE_URL` · `AI_API_KEY` · `AI_MODEL` 세 값만 바꾸면 OpenRouter, 유료 모델, 사내 AI 서버 어디로든 옮길 수 있음.
호출은 60초가 지나면 끊고, 성공·실패 모두 `ai_calls`에 남김. 기록이 실패해도 답은 그대로 돌려줌.

### 분류에는 AI를 쓰지 않음

같은 특허가 매번 같은 분야로 가야 추이를 믿을 수 있음. AI는 같은 질문에도 답이 조금씩 달라짐.
그래서 규칙(CSV)으로만 분류하고, 무작위 100건 채점 → 규칙 보강을 반복해 정확도를 올렸음.

### 분류 기준은 코드 밖에

기준을 코드에 적으면 고칠 때마다 개발자가 필요함. CSV에 두면 분류 담당이 엑셀로 열어 고칠 수 있음.
`npm run classify`가 CSV를 DB 표로 옮기고 전체를 다시 분류함.

### KIPRIS는 아껴 씀

월 1,000번 한도라 아래처럼 아낌.

- 처음 한 번만 전체를 받고, 그 뒤로는 마지막으로 받은 날짜 이후만 받음
- 청구항은 미리 받지 않고 사용자가 누른 특허만 받음
- 개발 중에는 같은 요청의 답을 디스크에 저장해 두고 다시 씀
- 자동 갱신이 실패해도 한 시간마다 다시 부르지 않고 하루 쉼

### 자동 실행은 "며칠 지났나"로 셈

"매 분기 1일 새벽 4시" 같은 정해진 시각으로 돌리면, 그 시각에 서버가 꺼져 있을 때 그 분기를 통째로 놓침.
그래서 "마지막 성공 갱신에서 90일이 지났나"를 한 시간마다 확인함. 서버가 늦게 켜져도 켜지는 순간 밀린 일을 함.
따로 예약 프로그램(cron 등)을 안 쓰고 서버 안에서 돌리는 이유도 같음. 공용 서버라 예약 프로그램을 마음대로 등록할 수 없음.

### 키는 브라우저에 가지 않음

KIPRIS 키와 AI 키는 서버의 `.env`에만 있음. 화면은 서버에만 요청하고, 서버가 대신 KIPRIS와 AI를 부름.

## 8. 앞으로 바꿀 예정이거나 고민 중인 것

### AI 모델 → 유료 모델

지금은 기능 시험용 무료 모델임. 기능을 고도화할 때 유료 모델로 바꿀 예정이고, 담당 팀원에게 인계됨.
코드는 안 고치고 `.env`의 세 값만 바꾸면 됨. 바꾼 뒤에도 요약 검사는 그대로 둠.

### SQLite → 팀 PostgreSQL (검토 중)

팀 PostgreSQL DB를 받았음. 바꾸면 이렇게 달라짐.

| | 지금 (SQLite) | PostgreSQL로 바꾸면 |
|---|---|---|
| 화면·결과 | | 같음 (데이터를 그대로 옮기면) |
| 팀원끼리 데이터 | 370MB 파일을 복사해서 주고받음. 누가 재분류하면 서로 달라짐 | 한 곳에 있어 모두 같은 데이터를 봄 |
| 여러 사람이 동시에 쓰기 | 약함 | 안전함 |
| 속도 | 충분히 빠름 (0.07초) | 체감 차이 거의 없음 |
| 노트북에서 개발 | 됨 | 안 됨 (천안 서버 안에서만 접속) |
| 실수의 영향 | 내 파일에만 | 팀 전체 숫자가 바로 바뀜 → 쓰기 규칙 필요 |

**바꾸는 작업량:** DB를 쓰는 파일 18개, 쿼리 90곳, 트랜잭션 6곳을 결과를 기다리는 방식(`await`)으로 바꾸고,
SQLite 전용 문법(`datetime('now')`, `AUTOINCREMENT`, `INSERT OR REPLACE`, `?` 자리표시)을 PostgreSQL 문법으로 바꾸고,
특허 8.8만 건 · 분류 16.4만 줄을 옮긴 뒤 숫자가 그대로인지 확인해야 함. 하루~이틀 걸릴 것으로 봄.

**가벼운 대안:** 서버 안 한 곳에 `patents.db`를 두고 각자 `.env`의 `DB_PATH`로 그 파일을 쓰게 하면,
코드를 거의 안 고치고 데이터 공유만 해결할 수 있음. 서버 계정 사이의 파일 권한은 먼저 확인해야 함.
