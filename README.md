# LG Display 특허 트렌드 센싱

천안형 AI 교육 과제2 · 스폰서사 LG디스플레이 · 3팀 · 디스플레이 특허 자동 수집·분류·동향 분석 시스템

> **데모:** https://3-production-29617a15.up.railway.app (접속 비밀번호는 팀에 문의)
> 2026-11-18부터 Railway에서 운영 중임. 90일마다 새 특허를 받고, 분기마다 AI 동향 요약을 새로 만듦.
> 배포 방법은 [10장](#10-배포-railway), 백업·복원은 [11장](#11-db-백업과-복원), 못 한 것은 [12장](#12-못-한-것)에 있음.

## 1. 이 시스템이 하는 일

LG디스플레이와 경쟁사(삼성디스플레이, 중국 4사)의 한국 공개 특허를 자동으로 모아서 기술 분야별로 나누고,
어느 분야에서 출원이 늘고 줄었는지 숫자로 계산한 뒤, AI가 그 숫자를 읽고 동향을 한국어로 요약해 웹 화면 하나로 정리함.

예)

분기마다 KIPRIS에 들어가 세 회사 이름으로 특허를 검색하고, 새로 공개된 수천 건의 IPC 코드와 명칭을 하나씩 읽어
"이건 OLED 회로, 이건 LCD 광학"으로 나누고, 분야별로 작년과 올해 건수를 세서 증감률을 내고,
갑자기 많이 등장한 기술 용어를 찾고, 자사와 경쟁사를 비교한 보고서를 쓰는 일.

이걸 사람 손 없이 자동으로 처리함. 분류와 집계는 몇 초, AI 요약은 분야당 1~2분임.

## 2. 전체 그림 — 숫자로 보는 흐름

실제 DB 기준임 (2026-11-10).

```
   수집 88,197건
      │   자사 46,161 · 삼성디스플레이 39,522 · 중국 4사 2,514
      │
      │  규칙으로 기술 분야 판정 (AI 안 씀)
      ▼
   IPC 코드로 판정       66,730건  (75.7%)
   키워드로 판정          9,053건  (10.3%)
   명칭으로 판정          8,350건  ( 9.5%)
   초록으로 판정          2,212건  ( 2.5%)
   미분류                 1,852건  ( 2.1%)
      │
      │  DB에서 건수·증감률·급증 용어 계산 (AI 안 씀)
      ▼
   1차 4종 × 2차 8종 × 3차 50종 분야별 추이
   신기술 후보: 급증 용어 50개 + 초기 신호 20개
      │
      │  계산된 숫자만 AI에게 주고 문장을 쓰게 함
      ▼
   분기 자동 요약 13개 (전체 1 + 방식 4 + 기술 분야 8)
      │
      ▼
   화면 5개
```

수집한 특허의 97.9%가 기술 분야를 받음. 무작위 검증으로 잰 정확도는 약 85%임.
**숫자는 전부 DB가 계산하고, AI는 문장만 씀.** 이게 이 시스템의 핵심 원칙임.

## 3. 어디서 무엇을 가져오나

소스는 KIPRIS Plus Open API(특허·실용 공개·등록공보) 한 곳임.

| 회사 | KIPRIS 검색어 | 건수 | 가장 오래된 출원 |
|---|---|---|---|
| LG디스플레이 (자사) | 엘지디스플레이 | 46,161건 | 1987년 |
| 삼성디스플레이 | 삼성디스플레이 | 39,522건 | 2003년 |
| BOE | 보에 테크놀로지 | | |
| CSOT | 차이나 스타 옵토일렉트로닉스 | 중국 4사 합계 2,514건 | 1999년 |
| Tianma | 티안마 | | |
| Visionox | 비젼녹스 | | |

KIPRIS는 무료로 쓰면 한 달에 1,000번까지 부를 수 있음. 처음 전체 수집에 약 200번, 이후 새 특허 받기는 보통 4번 씀.

### 왜 "LG디스플레이"로 검색하지 않나

실제로 해봤음. `LG디스플레이`로 검색하면 **0건**이 나옴.
KIPRIS에 등록된 출원인 이름이 `엘지디스플레이 주식회사`이기 때문임. 그래서 `엘지디스플레이`로 검색함.

### 중국 회사는 이름을 걸러서 받음

KIPRIS 출원인 검색은 이름 일부만 맞아도 결과에 넣어 줌.
`티안마`로 검색하면 전혀 다른 회사인 "닝보 케**티안 마**그넷"까지 나옴.
그래서 받은 뒤 회사 이름이 정확히 맞는 것만 남김. Visionox는 한국 표기가 "비젼녹스"라서 이걸로 찾음.

## 4. 파이프라인 — 단계별 설명

특허 한 건이 화면의 숫자와 요약이 되기까지 거치는 과정임. 순서대로 설명함.

### 0단계 · 대상 회사 목록 읽기

어느 회사를 받을지는 `backend/src/kipris.js`의 `APPLICANTS`, `CHINA_APPLICANTS`에 적혀 있음.
회사를 추가하거나 빼려면 이 목록만 고치면 됨.

### 1단계 · 수집

KIPRIS에서 명칭, 초록, 출원인, 출원일·공개일·등록일, 상태, IPC 코드, 도면 주소를 받음.

- 처음에는 전체를 받고(`npm run collect`), 그 뒤로는 **마지막으로 받은 날짜 이후** 새로 공개·등록된 것만 받음.
- 중간에 끊겨도 다시 실행하면 이어서 받음.
- 개발 중에는 같은 요청을 디스크에 저장해 두고 다시 쓰기 때문에, 시험하느라 무료 한도를 낭비하지 않음.
- 출원번호 같은 긴 숫자가 숫자형으로 바뀌면 끝자리가 깨지기 때문에, 받은 값은 전부 문자로 다룸.

청구항은 여기서 받지 않음. 특허 1건당 KIPRIS를 1번 불러야 해서, 8.8만 건을 다 받으면 한도를 88번 넘김.
화면에서 "청구항 불러오기"를 누른 특허만 받아 저장함 (지금 29건).

### 2단계 · 저장

원본은 `patents` 테이블에 그대로 둠. **분류 결과는 다른 테이블(`classification`)에 따로 씀.**
분류 기준이 바뀌어도 원본은 건드리지 않고 분류만 다시 계산하면 되기 때문임.

### 3단계 · 기술 분야 분류 ★

여기가 숫자의 정확도를 정하는 곳임. 1차 → 2차 → 3차 순서로 정함.

- **1차(방식):** OLED · LCD · 공통 · 마이크로LED
- **2차(기술 분야):** 회로 · 광학 · 공정 · 소자 · TFT 소자 · 설계 · 기구 · 재료
- **3차(세부 기술):** 50종 (14장 참고)

판정 순서는 IPC 코드 → 키워드 → 명칭 → 초록임. 앞에서 정해지면 뒤는 안 봄.

**IPC 코드는 모두 보고 점수를 더함.** 처음에는 첫 번째 IPC 하나만 봤는데, 검토해 보니 5건 중 3건이 틀렸음.
첫 코드가 "액정 전반"처럼 넓은 코드이거나, 발명의 핵심이 아닌 부수 기술인 경우가 많았기 때문임.
그래서 대응표에 있는 IPC를 전부 보고, 2차 분야마다 점수를 더해 가장 높은 쪽을 고름.

**키워드는 띄어쓰기와 대소문자를 무시함.** 특허 문서에 "화소 회로"와 "화소회로"가 섞여 있기 때문임.

**장비 특허는 따로 잡음.** "라미네이션 장치", "검사 장치"처럼 공정 말 + 장치로 끝나는 명칭은 공정으로 봄.
이런 특허에도 패널 IPC가 붙어 있어서, 점수만 보면 광학이나 터치로 잘못 가는 일이 많았음.

**왜 AI로 분류하지 않나.** 같은 특허가 돌릴 때마다 다른 분야로 가면 추이 그래프를 믿을 수 없음.
그래서 무작위 100건을 사람이 채점하고 → 틀린 이유를 찾아 규칙을 고치는 일을 11번 넘게 반복해 정확도를 올렸음.

분류 기준은 코드가 아니라 CSV 파일(`backend/classification/`)에 들어 있음. IPC 대응 157줄, 키워드 361줄임.

### 4단계 · 집계

화면의 모든 숫자는 여기서 SQL로 계산함. AI는 쓰지 않음.

날짜 기준이 두 가지라 헷갈리기 쉬움.

| 화면 | 기준 | 이유 |
|---|---|---|
| 연간 출원 추이 그래프 | **출원일** | 기술이 언제 나왔는지 보려고 |
| 대시보드 숫자, 최근 공개 동향 | **공개일** | 최근에 무엇이 새로 보이기 시작했는지 보려고 |

**최근 1~2년 출원은 음영과 점선으로 표시함.** 특허는 출원하고 보통 18개월 뒤에 공개됨.
그래서 2025년 출원은 아직 대부분 안 보이고, 그래프로 그리면 출원이 폭락한 것처럼 보임.
실제로 줄어든 게 아니라 아직 공개가 안 된 것이라서, 실선 대신 점선으로 그리고 "미공개 출원 반영 전"이라고 적음.

**1년 전 건수가 30건 미만이면 증감률을 안 보여 줌.** 2건이 5건이 되면 +150%인데, 이런 숫자는 의미가 없음.

### 5단계 · 신기술 탐지

최근에 갑자기 많이 나온 용어를 찾음. 이것도 AI 없이 계산함.

1. 명칭과 초록에서 1~3어절짜리 명사구를 뽑음
2. 한 특허에 여러 번 나와도 1번으로 셈
3. 전체 특허의 8% 넘게 나오는 흔한 말("표시 장치" 같은)은 뺌
4. 최근 2년과 그 전 4년을 통계(로그우도비)로 비교해 **우연이 아닌 증가**만 남김
5. "OLED"와 "유기 발광"처럼 뜻이 같은 표기는 하나로 묶음

실제 결과 (최근 2년 9,141건 vs 그 전 4년 16,024건):

```
화소정의막      371건 → 481건
회로층          193건 → 312건
증착용 마스크    11건 →  92건
멤브레인          0건 →  64건   ← 초기 신호 (예전엔 없던 말)
반사 전극        28건 →  87건
```

예전에 0건이었다가 최근 3건 이상 나온 용어는 "초기 신호"로 따로 보여 줌. 지금 20개임.

### 6단계 · AI 동향 요약 ★

AI가 분야 하나의 흐름을 정해진 다섯 칸(핵심 흐름, 성장 분야, 경쟁사 동향 등)으로 정리함.

**AI에게는 계산이 끝난 숫자만 줌.** 건수, 증감률, 비중, 급증 용어, 근거 특허를 DB에서 먼저 계산해 넘기고,
AI는 그걸 읽고 문장만 씀. AI가 직접 세거나 계산하게 하면 숫자를 지어내기 때문임.

근거 특허는 "가장 많이 늘어난 세부 기술"에서 최근 공개순으로 뽑음. 중요도 순위는 아님.

**설정만 바꾸면 다른 AI로 교체됨.** AI를 부르는 코드는 `backend/src/ai.js` 한 곳뿐이고,
주소·키·모델 이름 세 가지만 바꾸면 OpenRouter든 사내 AI 서버든 그대로 동작함.
배포 서버는 운영팀이 준 OpenRouter 키로 Claude Haiku 5.5(`anthropic/claude-haiku-5.5`)를 씀. 개발 초기에는 무료 모델로 기능을 시험했음.

### 7단계 · 요약 검사

AI가 쓴 요약을 코드가 다시 읽고 문제를 찾아 화면에 표시함.

| 검사 | 찾는 것 |
|---|---|
| 이상한 숫자 | 넘겨준 자료에 없는 숫자 |
| 특허 섞임 | 특허 A 설명에 특허 B 내용이 들어간 것 |
| 과한 해석 | "주력", "집중하는", "중단"처럼 회사 의도를 단정하는 말 |
| 형식 | 다섯 칸 중 빠진 칸 |

실제로 이번 분기 자동 요약 13개 중 **4개만 검사를 깨끗하게 통과**했음.
과한 해석 5개, 특허 섞임 4개, 이상한 숫자 3개, 형식 1개가 걸렸음 (한 요약에 여러 개 걸리기도 함).
그래서 검사 결과를 숨기지 않고 요약 위에 그대로 보여 줌.

### 8단계 · 자동 실행

서버가 켜져 있으면 한 시간마다 확인하고 알아서 돌림.

- **새 특허 받기:** 마지막으로 성공한 갱신에서 90일이 지나면 실행함.
  정해진 날짜가 아니라 "마지막 갱신으로부터 며칠"로 세기 때문에, 서버가 그날 꺼져 있었어도 다시 켜지면 밀린 걸 바로 함.
  실패하면 한 시간마다 다시 부르지 않고 하루 쉼.
- **AI 동향 요약:** 분기가 바뀌면(1·4·7·10월) 13개를 새로 만듦. AI가 바쁘면 잠깐 쉬었다 다시 시도하고,
  중간에 실패한 것은 6시간 뒤 이어서 만듦.

그래서 화면에 새로고침 버튼이 없음.

### 9단계 · 화면

DB에서 숫자를 꺼내 그래프와 표로 그림. 그래프는 라이브러리 없이 SVG로 직접 그림.
음영, 점선, 키보드로 값 보기처럼 이 프로젝트에만 필요한 표시를 자유롭게 넣기 위해서임.

특허를 누르면 상세 창이 열림. 초록과 대표 청구항, 분류 결과와 그 근거, 도면, 개별 특허 AI 요약을 볼 수 있음.
맨 위 검색창에서 기술 키워드(예: 탠덤, 봉지)를 바로 찾을 수 있음.

### backend/data/patents.db

데이터가 실제로 쌓이는 곳. 파일 하나가 곧 데이터베이스임.

이걸 지우면 KIPRIS에서 다시 받아야 함(약 200번 호출). 깃허브에 올라가지 않으니 팀 안에서 파일로 주고받음.

## 6. 직접 돌려보기

### 준비물

Node.js 22.12 이상만 있으면 됨. [nodejs.org](https://nodejs.org)에서 LTS를 받거나 아래 명령으로 설치함.

```powershell
winget install OpenJS.NodeJS.LTS
```

설치 후 VS Code를 완전히 껐다 켜고 `node -v`로 확인함.

### 필요 사양

| 항목 | 필요한 것 |
|---|---|
| Node.js | 22.12 이상 |
| 메모리 | 평소 약 270MB, 많을 때 약 570MB (천안 서버에서 잰 값) |
| 디스크 | DB 약 225MB(정리본) + 여유. 오래 쓴 DB는 작업 기록 때문에 더 커질 수 있음 (천안 서버 원본 약 370MB) |
| 네트워크 | KIPRIS와 AI 서버로 나가는 https 연결 |
| 브라우저 | 최신 Chrome·Edge. 휴대폰 화면도 지원 |

### 1. 파일 받기

```powershell
git clone https://github.com/Eom-Jeongung/3-.git
cd 3-
```

`main` 브랜치가 최신 코드이고, 배포 서버도 이 브랜치를 씀.

이미 받았다면 최신으로 갱신함.

```powershell
git pull
```

### 2. 라이브러리 설치

```powershell
npm run setup
```

### 3. 열쇠(API 키) 넣기

`backend/.env.example`을 복사해 `backend/.env`를 만들고 값을 넣음. 값은 팀 안에서 공유받을 것.

```
KIPRIS_API_KEY=여기에_인증키
AI_BASE_URL=https://openrouter.ai/api/v1
AI_API_KEY=여기에_키
AI_MODEL=여기에_모델이름
API_PORT=4000
```

- 화면만 볼 거면 키가 없어도 됨
- `=` 앞뒤에 띄어쓰기 넣지 말 것. 따옴표도 필요 없음
- 천안 서버에서는 `API_PORT`를 비워 둘 것
- 배포 서버에서만 `SITE_PASSWORD`를 넣음. 넣으면 화면과 API 전체에 비밀번호가 걸림
- 이 파일은 깃허브에 올라가지 않음. 키를 채팅방·문서·캡처에 올리지 말 것

### 4. 데이터 넣기

팀에서 받은 `patents.db`를 `backend/data/`에 넣으면 끝임.
서버를 끈 상태에서 넣고, `patents.db-shm`, `patents.db-wal`이 있으면 지울 것.
압축 백업 파일을 받았다면 [11장](#11-db-백업과-복원)의 복원 순서를 따름.

### 5. 실행

```powershell
npm run dev
```

백엔드와 화면이 함께 켜짐. 화면에 이런 줄이 보이면 정상임.

```
[API] [자동 요약] 켜짐: 분기마다 (지금 2026년 4분기)
[API] [자동 갱신] 켜짐: 마지막 갱신 후 90일마다
```

브라우저에서 http://localhost:5173 을 열면 됨. 천안 서버에서는 VS Code 아래 PORTS 탭의 내 포트를 엶.

### 실행 명령

| 명령 (루트에서) | 언제 쓰나 |
|---|---|
| `npm run dev` | 평소. 화면과 서버 켜기 |
| `npm run sync` | 새 특허만 지금 받기 (자동 갱신을 기다리지 않을 때) |
| `npm run classify --prefix backend` | 분류 기준(CSV)을 고친 뒤 전체 재분류. KIPRIS 안 부름 |
| `npm run auto-summary --prefix backend` | 분기 AI 요약을 지금 만들기 |
| `npm run auto-summary --prefix backend -- --all` | 이번 분기에 만든 것까지 전부 다시 (프롬프트를 고쳤을 때) |
| `npm run collect --prefix backend` | 전체 수집. **주의** |

`collect`는 KIPRIS를 약 200번 부름. 한 달 무료 한도가 1,000번이라 팀에서 한 번만 돌릴 것. 평소에는 쓰지 말 것.

## 8. 자동 실행

서버가 켜져 있는 동안 알아서 돎. 따로 할 일 없음.

| 무엇 | 언제 | 끄는 법 |
|---|---|---|
| 새 특허 받기 | 마지막 갱신 후 90일마다 | `.env`에 `SYNC_INTERVAL_DAYS=0` |
| AI 동향 요약 13개 | 분기마다 (1·4·7·10월) | `.env`에서 `AUTO_SUMMARY` 지우기 |

**AI 요약 자동 실행은 서버에서만 켤 것.** 노트북에서도 켜면 같은 AI 키로 두 번 만들어 사용량을 두 배로 씀.

서버가 꺼져 있으면 아무것도 안 돎. 다시 켜면 밀린 것부터 처리함.

## 9. 이 시스템의 한계

### 분류는 약 85%만 맞음

무작위 100건을 채점해서 잰 값임. 100건 중 15건쯤은 다른 분야로 들어가 있음.
특히 3차 "기타"가 6,635건(7.5%)으로 많음. 세부 기술 키워드를 더 보강해야 함.

### 최근 1~2년 출원은 아직 다 안 보임

특허는 출원 후 약 18개월 뒤 공개됨. 2025~2026년 출원은 지금 보이는 게 전부가 아님.
그래프의 점선 구간을 "줄었다"로 읽으면 안 됨.

### AI 요약은 아직 시험 단계임

개발 중 무료 모델로 만든 이번 분기 자동 요약은 13개 중 9개가 검사에 하나 이상 걸렸음.
자료에 없는 숫자를 쓰거나, 특허 A를 설명하면서 특허 B 내용을 섞거나, "주력한다"처럼 회사 의도를 단정했음.

배포 서버는 Claude Haiku 5.5로 바꿨음. 배포 주소에서 시험한 요약 1건은 35초 걸렸고 숫자 불일치는 0건이었음.
다만 여러 모델을 같은 조건으로 비교 평가하는 일은 아직 못 함.
설정 세 줄(`AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL`)만 바꾸면 되도록 만들어 둠.
모델을 바꿔도 검사는 그대로 두고, 중요한 숫자는 근거 표와 근거 특허로 확인하는 게 안전함.

### 중국 4사는 실제보다 작게 보임

한국 특허청에 낸 출원만 집계함. 중국 본토 출원은 안 들어 있음.
Tianma는 최근 5년 한국 출원이 0건이라 그래프에 거의 안 보임.

### 패밀리·후속 출원이 같이 세어짐

같은 기술을 여러 건으로 나눠 낸 것도 각각 1건으로 셈. 특정 연도 증가폭이 실제보다 크게 보일 수 있음.

### 마이크로LED는 아직 표본이 적음

1차 마이크로LED는 86건뿐임. IPC 코드(`H10H`)만으로는 일반 LED(백라이트 등)가 섞여서,
본문에 "마이크로 LED"가 나올 때만 마이크로LED로 봄.

### KIPRIS 한도가 있음

KIPRIS는 월 1,000번 한도라 전체 수집을 자주 할 수 없음. 그래서 새 특허만 받는 방식으로 돌림.

### 공용 서버 하나에서만 돎

DB가 SQLite 파일 하나라 여러 서버에서 같이 쓸 수 없음. 서버가 꺼져 있으면 자동 갱신도 안 돎.

## 10. 배포 (Railway)

화면·서버·DB를 Railway 서비스 하나에 올림. 서버 하나가 화면과 API를 함께 보내고, DB 파일은 볼륨에 둠.

| 항목 | 설정 |
|---|---|
| 플랜·지역 | Railway Hobby (결제 전까지 체험판), Southeast Asia (Singapore) |
| 저장소·브랜치 | `Eom-Jeongung/3-` · `main` (합치면 자동으로 다시 배포됨) |
| Build Command | `npm ci --prefix backend --omit=dev && npm ci --prefix frontend --include=dev && npm run build` |
| Start Command | `npm start` |
| Healthcheck Path | `/api/health` (비밀번호 없이 열림, 데이터 없음) |
| 볼륨 | `/data` (DB는 `/data/patents.db`) |

환경변수는 Railway의 Variables에 넣음. 키와 비밀번호는 채팅·문서에 적지 말 것.

| 이름 | 값 | 이유 |
|---|---|---|
| `PORT`, `API_PORT` | `8080` | Railway 공개 포트와 서버 포트를 맞춤 |
| `NODE_VERSION` | `22` | Node 22.12 이상 필요 |
| `DB_PATH` | `/data/patents.db` | 없으면 다시 배포할 때 DB가 사라짐 |
| `SITE_PASSWORD` | 팀 공용 비밀번호 (12자 이상) | 주소만 알면 누구나 AI 요약을 눌러 비용을 쓸 수 있어서 |
| `KIPRIS_API_KEY` | 발급받은 키 | 자동 갱신, 청구항 |
| `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL` | `https://openrouter.ai/api/v1`, 운영팀 키, `anthropic/claude-haiku-5.5` | AI 요약 |
| `SYNC_INTERVAL_DAYS` | `90` | 자동 갱신 주기 |
| `AUTO_SUMMARY` | `1` | 분기마다 동향 요약 13개 |

알아 둘 것

- 비밀번호를 10번 틀리면 그 접속 주소는 15분 동안 막힘. Railway가 알려 주는 실제 접속 주소(`X-Real-IP`)로 셈
- 다시 배포하는 동안 잠깐 접속이 끊김. 수정은 모아서 합치고, 시연 직전에는 `main`에 합치지 말 것
- 배포 서버가 자동 갱신·자동 요약을 맡으므로 천안 서버 `.env`는 `SYNC_INTERVAL_DAYS=0`, `AUTO_SUMMARY`는 비워 둠. 둘 다 켜면 KIPRIS·AI 한도를 두 번 씀
- 콘솔(Railway → 서비스 → Console)에서 `node`가 안 잡히면 먼저 이 줄을 실행함

```bash
export PATH="$(ls -d /mise/installs/node/*/bin | head -1):$PATH"
```

## 11. DB 백업과 복원

### 백업 (서버를 켠 채로 가능)

`VACUUM INTO`로 빈 공간을 뺀 정리본을 만들고 압축함. 주 1회와 실습서버 종료 전에 함.

```bash
cd /app/backend
node -e 'require("better-sqlite3")("/data/patents.db",{readonly:true}).exec("VACUUM INTO \x27/tmp/patents-backup.db\x27")'
node -e 'const d=require("better-sqlite3")("/tmp/patents-backup.db",{readonly:true});console.log(d.pragma("integrity_check",{simple:true}),d.prepare("select count(*) n from patents").get().n)'
gzip -9 /tmp/patents-backup.db
sha256sum /tmp/patents-backup.db.gz
```

- 두 번째 줄 결과가 `ok`이고 특허 건수가 화면과 같으면 정상임
- Railway에서는 압축 파일을 `/app`으로 복사한 뒤, 콘솔 아래 파일 창에서 파일을 오른쪽 클릭 → Download로 받음. 받은 뒤 `/app`과 `/tmp`의 복사본은 지움
- 볼륨(`/data`)에는 정리본을 만들지 말 것. 체험판 볼륨은 약 430MB라 DB 두 개가 들어가지 않음
- 백업 파일과 검증값(SHA-256)은 깃허브에 올리지 말고 팀 안에서 보관함

### 복원

1. 받은 압축 파일의 검증값이 백업할 때 적은 값과 같은지 확인함 (`sha256sum`)
2. 압축을 풀고 위 확인 명령으로 `ok`와 건수를 확인함
3. 서버를 끄고 `patents.db`를 교체함. 같은 폴더의 `patents.db-shm`, `patents.db-wal`은 지움
4. 서버를 켜고 화면의 건수와 마지막 갱신 시각을 확인함

Railway에서는 콘솔 파일 창의 Upload로 압축 파일을 `/data`에 올리고, 콘솔에서 1~3을 한 뒤 서비스를 Restart함.

## 14. 분류 체계

팀 문서 "LG디스플레이 특허 트렌드센싱 v0.2 기술 분류 체계"를 바탕으로, 검증하며 고친 기준 v0.5.5임.

### 1차 · 방식 4종

| 방식 | 건수 |

## 15. 분류 기준이나 대상 회사를 바꾸고 싶다면

### 분류 기준

`backend/classification/` 안의 CSV를 고침.

`ipc_map.csv` — IPC 코드로 분야 정하기

```
ipc_prefix,level1,level2,level3
H10K,OLED,,
H01L 51,OLED,,
```

`keyword_map.csv` — 키워드로 분야 정하기

```
level1,level2,level3,keyword,requires
OLED,,,유기발광,
OLED,,,OLED,
```

같은 형식으로 한 줄을 추가하면 됨. `H10K`처럼 앞자리만 적으면 그 그룹 전체, `G02F 1/13`처럼 `/` 뒤까지 적으면 그 숫자로 시작하는 코드만 해당함.
같은 코드에 여러 줄이 맞으면 가장 길게(구체적으로) 적힌 줄을 씀.

고친 뒤 재분류함. KIPRIS는 안 부름.

```powershell
npm run classify --prefix backend
```

고치기 전에 팀에 먼저 알릴 것. 분류가 바뀌면 모든 화면의 숫자가 바뀜.

### 대상 회사

`backend/src/kipris.js`의 `APPLICANTS`(자사·삼성)와 `CHINA_APPLICANTS`(중국 4사)를 고침.
회사를 추가했다면 그 회사 특허를 새로 받아야 함 (KIPRIS 호출 필요).

문의나 오류 제보는 팀 채널에 남길 것.
